## Why Terragrunt?

Managing Terraform at scale is powerful but often messy. As teams grow, configuration sprawl, code duplication, and environment drift start slowing everything down.  
That’s where **Terragrunt** changed the game for us.

Over the past few months, we’ve refactored multiple AWS infrastructure stacks — from CI/CD pipelines to disaster recovery — using Terragrunt.  
The result? Fewer lines of code, faster deployments, and much saner infrastructure management.

---

## Before Terragrunt: Terraform Sprawl

Without Terragrunt, every environment (`dev`, `qa`, `prod`) had its own Terraform directory.

- Repeated backend configuration  
- Copied provider blocks  
- Manual state file paths  
- Complex environment drift

This often led to **long deployment times** and **risky rollouts**.

---

## After Terragrunt: DRY Infrastructure as Code

Terragrunt enforces a **“Don’t Repeat Yourself” (DRY)** structure using a simple `terragrunt.hcl` file that centralizes all repetitive settings.

It helps:

- Reuse remote backend configs  
- Automate dependency handling between modules  
- Keep variables consistent across environments

## Cost comparison (example using GitHub-hosted runner pricing)

Below we show how to translate time saved into money saved using GitHub-hosted runner pricing as the base rate. GitHub publishes per-minute billing rates for GitHub Actions (varies by OS and plan) — always check the current pricing page: https://docs.github.com/actions/billing. In general the calculation is:

- Base rate (C) = cost per minute for the chosen runner (dollars / minute). For GitHub-hosted runners this depends on OS: Linux is typically the cheapest, macOS and Windows are higher.
- Per-run cost = runtime_minutes * C
- Monthly cost = Per-run cost * R (runs per month)

### How we measured execution time (reproducible)

To compare real-world run times, run the same sequence of operations on both layouts and average multiple runs. On Windows PowerShell you can use `Measure-Command` to capture wall-clock time. Example workflow:

1. Ensure both setups use the same module code and remote backend settings (only orchestration/layout differs).
2. Warm up caches (run a single init/plan and discard the result).
3. Run N trials and average.

PowerShell timing snippet (repeat and average):

```powershell
# Terraform-only: sum plan times for each env (example for one env)
$tf = (Measure-Command { terraform -chdir=live/dev init -input=false -no-color }).TotalSeconds
$tf += (Measure-Command { terraform -chdir=live/dev plan -input=false -no-color }).TotalSeconds
Write-Output "Terraform (dev) total: $tf s"

# Terragrunt: single command across the repo
$tg = (Measure-Command { terragrunt run-all init --terragrunt-non-interactive }).TotalSeconds
$tg += (Measure-Command { terragrunt run-all plan --terragrunt-non-interactive }).TotalSeconds
Write-Output "Terragrunt run-all total: $tg s"
```

Best practice: run the above 5 times, discard the first (cold-start), and average the remaining 4 runs to reduce noise.

### Translating time into cost savings

Use this simple formula to convert time saved into approximate CI runner cost saved:

Let:
- T_tf = total Terraform-only time (seconds)
- T_tg = total Terragrunt time (seconds)
- C = runner cost (dollars per minute)

Time saved per run: ΔT = T_tf - T_tg (seconds)

Cost saved per run: ΔCost = C * (ΔT / 60)

Monthly saving (R runs/month): Monthly = R * ΔCost

Worked example (using metrics from this post):

- T_tf ≈ 40 minutes = 2400 seconds
- T_tg ≈ 18 minutes = 1080 seconds
- ΔT = 1320 seconds = 22 minutes
- If runner cost C = $0.05 / minute → ΔCost = 0.05 * 22 = $1.10 per run
- If pipeline runs R = 50 times/month → Monthly ≈ $55/month

Notes:
- These numbers are illustrative. Real savings depend on parallelism, number of modules, provider API response times, and whether CI time is billed per minute or as pooled capacity.
- Terragrunt's `run-all` parallelism often reduces elapsed wall-clock time compared to sequential `terraform` runs invoked from scripts.

### Practical tips to maximize savings

- Centralize remote state and provider config so child modules don’t re-run redundant initializations.
- Use `terragrunt run-all plan --terragrunt-parallelism N` to tune parallelism (higher N where resources are independent).
- Cache provider plugins between runs when your CI supports workspace caching to reduce `init` time.

## CI/CD Integration

We integrated Terragrunt with **AWS CodePipeline + CodeBuild**, letting pipelines run full environment builds with:

- `terragrunt validate-all`  
- `terragrunt run-all plan`  
- `terragrunt run-all apply`  

The same pipeline now supports **multi-region and blue/green DR** deployments — cutting CI/CD setup time by **~40%**.
